# 导演助手对话栏（2026-10-09）

> 状态：代码、自动化测试与本机真实运行见文末「验收证据」。这是导演 Agent 四期里的第二期（第一期「从剧情开始」见 `docs/story-entry-phase1-2026-10-09.md`）。一句话修改剧情/分镜（第三期）和 4.0 分镜批量出视频（第四期）不在本期。
>
> 命名：本文说的「第二期」只指导演 Agent 的四期计划，与 AGENTS.md 里「Phase 2 Cast / Character Governance」「Phase 2 只预留 Candidate 接缝」无关。

## 1. 它是什么

页面右侧的对话栏（类似 Lovart 右侧的 Agent）：

- 知道用户做到了哪一步，提议下一步，并在卡片上写明花费；
- 用户点卡片上的「确认执行」后，执行的是页面上那个按钮背后的**同一段代码**（`public/app.js` 的 `executeDirectorAgentAction`）；
- 每一步做完，给一段只报计数的总结；失败时写出原因（含供应商原文），审核拦截时说明不会自动重试；
- 参考视频和剧情两个入口都能用。

用户已定的三件事：打字由文本模型理解；文本步骤估钱、出图和视频只报数量；第二期只走主线。

## 2. 两条硬约束决定的分工

`docs/GitHub-Benchmark-后续改造待办.md` 明确排除了两件事：可变的 Agent 对话成为事实来源（:283），以及多 Agent 自由编排作为业务状态机（:467）。所以分成两半：

| | 由谁决定 | 在哪 |
|---|---|---|
| 现在能做哪几步、下一步是什么、每步花多少 | 固定规则，从页面状态算 | `public/director-agent-progress.js` |
| 用户打的字对应哪一步、怎么回一句话 | 文本模型，只能从上面那份清单里选 | `POST /api/director-agent/turn` |
| 真正执行 | 用户点卡片上的「确认执行」 | 页面原有函数 |

模型永远不能直接执行；用户打字说「好的」也不会执行，只有点卡片按钮才执行。另外 `:477` 禁止默认选第一个候选，所以**挑故事候选只做成按钮，不进模型能选的清单**（`DIRECTOR_AGENT_ACTIONS.chooseCandidate.modelSelectable = false`，服务端在请求里看到它就 400）。

## 3. 主线动作

| 动作 | 调用的现有函数 | 花费（卡片上写的是下限） | 什么时候提 / 不提 |
|---|---|---|---|
| `startPipeline` 开始 AI 导演 / 开始或继续拆镜头 | `runWorkflow` | AI 导演至少 6 次；拆镜头 3 次（粘贴故事）或 2 次（只给设定）；已完成的步骤不重跑 | 设置填好就提。参考视频入口**只在还没有候选时提**（已有候选再点会直接开新 Run、没有确认）；剧情入口只在从头开始或原文没改过的「继续」时提；暂停中只提示去点页面上的继续 |
| `regenerateCandidates` 换一批 | `regenerateThemeVariants` | 至少 2 次 | 只在参考视频入口、还没有任何完整剧情和分镜时提 |

| `generateStoryboard:<V>` 生成分镜 | `generateAnimationPlan({force:false})`（先跳到分场页） | 至少 2 次，审阅报出问题时再修订、终审 | 有剧情、没分镜。卡片列出会写进分镜的画幅、画风、配乐 |

| `openShotVideo:<V>:<shot>` 打开镜头视频弹窗 | `openShotVideoGenerator` | 视频，在弹窗里确认；没写过这一镜的提示词时打开就先调用 1 次文本模型 | 没有视频的镜头。**不替用户预选「全能参考」模式**（§2.6 禁止按缺少首尾帧推断模式），弹窗自己会提示 |

任何弹窗开着、或有步骤在跑时，不提任何可执行动作（避免并行发起付费任务）。执行后立刻检查对应的「正在运行」标记；函数什么都没做就直接返回时，如实写「没有开始」并引用页面上的提示文字。

## 4. 卡片与核对

- 每个动作带自己的 `guard`：它依赖的 Run、工作区 epoch、故事/分镜版本，以及卡片上显示的画幅、画风、配乐、模型。
- 点「确认执行」时重新算一遍进度：动作不在清单里了、或 `guard` 对不上，卡片作废，并给出新的建议。
- 同一时间只留一张待确认的卡；同一个动作、核对项没变时不重复发卡；换了 Run 时作废旧卡。

## 5. 花费怎么写

- 文本步骤：「至少调用 N 次」（下限，来自代码结构，`DIRECTOR_AGENT_MIN_TEXT_CALLS` 一张表）+「这个 Run 上次同类步骤：M 次调用 · 用了 X tokens · 约 ¥Y」。¥ 只在 `MODEL_PRICE_CNY_PER_MILLION` 里配了单价时显示（`formatStageUsageSuffix` 的既有规则）。参考视频入口的「上次同类」只算展开完整剧情那一个任务，不含展开前体检（体检不是任务，没有记录）。
- 出图与视频：只写数量与计费方式，不估价（单价未知）。
- 导演助手自己的每条回复下面显示这条消息用了多少 token。它的请求**不走 `api()`**：`api()` 会把用量记进正在进行的那一步，一条对话的花费就混进了体检或分镜的合计。

已知：本机 `.env` 的单价表没有 mimo-v2.6 系列，还有一条 DeepSeek 的写法解析不了，所以目前 MiMo 的步骤只显示 token。

## 6. 「这一步做完了」怎么判断

任务显示「完成」时，新结果还要再等一次 `/run/load` 才进页面（`waitForDurableTask` 先回报完成快照，调用方随后才 reload）。只看任务状态从「运行」变「完成」，总结会报错数字或者报早了。所以对比两样东西：

1. 定义各步骤的 Artifact 当前版本与计数（流水线完成标记、候选版本、有参考图的角色、有视频的镜头）；
2. 哪些任务的结果已经是当前版本（`taskForUi` 只在结果进了页面之后才返回完成的任务）。新生成的分镜靠这一条认出来，与「设为人物参考图」签发的新分镜版本区分开。

刷新钩子挂在 `updateTaskSnapshot`、`reloadActiveProductionRun`、`acceptProductionCommit`、首页与分场页的渲染、`resetDirectorClientState`，合并成一次刷新；另有 1.5 秒的兜底定时器接住展开前体检这类不经过任务轮询的变化。第一次观察（以及换了 Run 或工作区之后）只记基线、打招呼，不把已完成的步骤再报一遍。

**导入测试包（2026-10-10，随剧情 Run 的 3.1 包一起改）**：
- 导入剧情包要先设上新 Run、再从服务端读回内容，读回之前页面是半截的。这段时间对话栏不观察（`storyRunImporting`，与页面初次恢复同一个开关 `restored`），否则会把半截状态报成「原文或剧情模式改过了」「可翻拍镜头拆好了」——演示模式真实运行里撞上过。
- 读回之后按换 Run 处理：原来有 Run 时说「已经换成新的 Run。」；原来没有 Run、换上来的 Run 已经有结果（流水线完成标记是当前版本）时说「已经打开新的 Run。」，作废旧卡、按新进度提议。只有导入会走到后一条，参考视频的包同样适用；刚开始跑的新 Run 还没有结果，照旧不说话，等那一步做完再报。

## 7. 模型那一半：`POST /api/director-agent/turn`

- **只出建议**：与剧情体检同规格，不签发 Artifact、不进 lineage、不建任务、不写盘，同步执行并统计用量。
- **输入**（`src/director-agent.js` 在调用模型之前核，超限一律 400）：
  - `message` ≤ 500 字；
  - `history` ≤ 6 条，只有用户的话和导演助手之前的回复，每条 ≤ 400 字；
  - `progress`：入口、步骤（状态 + 计数）、正在进行、在等什么、补充说明（≤ 3 条）、下一步编号、模型能选的动作（编号 + 固定标签 + 花费类型）。**不含故事原文、候选标题、模型写的任何文字、供应商报错原文或提示词**，免得这些文字里夹带指令。动作标签里只有短的角色名（截到 12 字）。
- **补充说明**（`progress.notes`）：由规则写出「某一步为什么不在清单里」「顺序是不是硬性要求」。实测没有它时，用户问「先做第二镜」，模型自己编了一个原因（「要先出角色参考图」），真实原因是镜头视频模型是可灵、写不了 4.0 单镜提示词；加上之后同一句话答对了。
- **输出**：`{actionKey, reply}`。严格 Schema（`src/contracts/schemas/director-agent-turn-strict.schema.json`）+ 编号必须在这一轮的清单里或是 `none`（`DIRECTOR_AGENT_ACTION_NOT_OFFERED`）。MiMo 用约束解码，模型侧 Schema 从严格 Schema 派生，枚举就是这一轮的清单加 `none`。
- **调用**：走 `modelCallCoordinator.runJson`，最多 2 次、禁止第三次；第二次仍不对就如实报错（两次的诊断都在），不拿确定性答案顶替；审核拦截不重试。每次都关闭思考（见 §8）。调试侧车 scope `directorAgent`，自己接 `attemptObserver`。
- **阶段**：`directorAgent`，默认用默认文本模型，输出上限 8192；模型设置里是可选的一行「导演助手」。
- 页面拿到回复后按**当时的**进度找编号：找不到就不出卡片，说明「进度刚刚变了」。

## 8. 单次请求的思考开关

三家文本客户端的思考开关原来只有全局配置，本机 `.env` 开着 MiMo 思考，一条对话会推理很久。`requestCompletion` 新增可选的 `thinking: "enabled" | "disabled"`（`src/thinking-override.js`），只有导演助手会传；不传时三家的请求体逐字不变（`test/text-client-thinking-override.test.js` 用改动前算出的金标准锁住，键的顺序也锁）。千问的 GLM-5.3 关不掉思考，要求关闭时客户端抛带码的 `ModelResponseError`（`MODEL_THINKING_UNSUPPORTED`，不用 TypeError——协调器会把 TypeError 当成网络故障重试），工作流在调用之前先给出 400。

## 9. 存储

对话只放在页面内存里：不进 Task Store、Artifact、localStorage、sessionStorage，刷新即清空，刷新后按当前进度重新打招呼。展开状态也不保存（长期存储只能放创作宇宙那七项设置）。导演助手的模型覆盖照常进 sessionStorage，这是现有规则允许的。

## 11. 已知局限

- **模型回复的文字没有确定性兜底**：只有 `actionKey` 受校验。回复标成「AI 回复（可能说错，以卡片为准）」，卡片上的数字都由规则算出。登记为待解决项第 21 条。
- 调用次数是下限；重试、审阅后的修订都会多花，跑完会显示实际用量。
- 剧情准备和分镜仍不能暂停或终止（要改任务管理器核心，本期不做）。
- 体检、评审、修订、采纳、重新开始，以及换配乐、画幅、画风，仍在页面上做；4.0 分镜没有批量视频（第四期）。

**真实运行暴露、当场修好的四个问题**（都补了测试）：

1. 用户问「先做第二镜」时，模型自己编了原因（「要先出参考图」），真实原因是镜头视频模型是可灵 → 加 `progress.notes`（补充说明），之后同一句话答对了。
2. 页面初始化还没读完模型设置时就能发消息，进度按默认的可灵算，模型提了「打开模型设置」，回复到达时已不需要（对话栏如实说「进度刚刚变了」）→ 初始化全部完成前不观察、不发消息，发送按钮置灰。
3. 模型选的动作已经有一张待确认的卡、但卡被后面的消息压在上面 → 挪到最下面，旧位置标「已移到下面」。
4. 刚打开时等待提示说了两遍；手机上顶栏按钮被挤成两行 → 已改。

**D 页面**：宽屏（1440）对话栏推开页面内容；中等宽度（1024）默认收起、打开后盖在页面上；手机（375）是底部面板（约 72% 高）；三种宽度都没有横向滚动。出图与镜头弹窗都盖在对话栏上面。

**没覆盖到的**：参考视频入口只验证了打招呼与卡片，没有用真实视频跑 AI 导演；「只给角色设定」只在自动化测试里跑过；出图、选参考图之后的总结只在自动化测试里验证。
