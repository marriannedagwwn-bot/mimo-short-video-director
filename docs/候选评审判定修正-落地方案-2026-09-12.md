# 落地计划：候选对照评审的三处判定修正

2026-09-12。这份计划可以独立执行，需要的实验依据都写在里面。

---

## 一、为什么是这三处，以及为什么**不是**别的

过去两天跑了五组真实实验（约 60 次模型调用）。**生成侧的四个想法全部被自己的数据否掉，判定侧的三处缺口被证实存在。** 这份计划只落地后者。

### 被证伪的，不要重做

| 想法 | 实测结果 | 结论 |
| --- | --- | --- |
| 用 `citationCoverage`（LCS）确定性算表面相似度 | 六组 24 个候选跨度只有 **0.049**（0.083–0.133），已知是「四个同一个故事」的那组只比最低的高 0.05 | **走死。** LCS 量字面重合，而换皮恰好换掉全部字面只留结构。那个函数的本职是「你引用的原片事实是不是真的」，不能反过来用 |
| 把 `storyEngine` 抽象成机制层 | **`storyEngine` 根本不进候选提示词**（`src/prompts.js:711` 明写它不进正向投影）。当时观测到的差异来自「改简报 → `sourceDigest` 失效 → 重签角色边界 → `allowedTraits` 多了一条『关爱长辈』」 | **归因错误，已撤回。** 改它对候选阶段无效 |
| Transfer Kernel：先规划四组机制再生成 | 三轮对照。预先规划组：兑现率 80% vs 54%、**与原片事件链重合 52.5 vs 40.0**、**盲评剧情质量 73.8 vs 85.6（六项全输）** | **更听话 + 更像原片 + 故事更差。** 见下节 |
| 修订 M2 的机制描述（v3） | v1 三个全是 force，v2 三个类别全不同，**v3 退回 2/3** 且写出两个「作弊」故事，与固定角色「乖巧懂事」冲突 | **v3 作废，v2 保留。** 机制描述改写有效但不可控 |

### Transfer Kernel 为什么失败——这条要记住

**顺序反了。** 自由挑组的实际顺序是「先有故事 → 再贴标签」；预先规划组是「先有标签 → 再造故事」。而模型面对明确清单时会找**最容易证明自己做到**的写法，那个写法就是**原片那个桥段**——因为那是这条机制唯一有现成范例的实现。

一条数据坐实：M2 描述是「两个角色在物理空间上的受力互补」，五次兑现里四次写成「一前一后同时使力」，其中一次是「小白子在前拉绳，小雅在后推板」——几乎逐字复刻原片的「咕嘎在前拉车，糯糯在后推车」。

**推论：`kernelFidelity` 这类「有没有照着做」的指标在系统性地惩罚好故事。** 自由写出来的故事兑现方式是顺带的、变形的，判定说「只沾边」；照机制造的故事兑现很干净，判定给满分。这与 `CLAUDE.md` §2.13 记的「评审→重写单轮只涨 +0.17」同构：**更合规 ≠ 更好**。

所以**不要**把机制迁移做成生成侧的硬约束。

## 二、要落地的三处（全在评审阶段）

评审只出报告、不改候选、不进 lineage、不 stale，改它的契约代价极低（§2.12b ④）。

### ① 情感与选择类机制的判定必须双证据

**问题**：现有 `mechanismChecks` 判 `depicted` 时只要看到末尾那个动作就通过。实测三次「已兑现」的证据：

- 「第 5 拍小白子把书签别在奶奶胸前」
- 「第 5 拍摘下星星徽章别在**芙芙猫**呆毛上」
- 「第 5 拍将书签夹进老馆长正在阅读的旧书里」

**三条全部只有转移动作，没有一条指出前因**——那东西是不是先真正属于她、她是不是在意、有没有舍不得。

按双证据标准重评后，这三条**全部降级为 `partially_depicted`**，整组兑现率从 70.8% 掉到 54.2%。

> **初稿在这里犯了一个旧错误，已改**：初稿否掉第二条的理由是「接收方是并肩搭档芙芙猫，
> 根本不是默默付出的关爱者」——那是**按角色身份名称直接判定**，与 §2.12b 禁止的词表分类、
> 与「普通植物被照料不构成角色身份」是同一类错误。**同伴也可以照顾主角。**
> 判据只能是：故事前面有没有写出相应的贡献或付出，写在哪一拍。

**改动**：`mechanismCheck` 的 `whereInCandidate` 拆成两个键：

```
"causeEvidence": ""   // 前因：这东西怎么成为她在意的；接收方此前做过什么
"actionEvidence": ""  // 兑现动作：哪一拍的哪个动作完成的
```

**双证据只要求机制真正需要前因的那些，不一刀切。** 判据挂在**共享清单**上：
`sourceMechanism` 新增必填 `requiresCause`（boolean）。主动付出、转赠、牺牲、承担成本、
反哺这类机制的分量全在前因上；而「会不会跑」「有没有陪着」根本不需要前因，
对它们也要两条证据就是在逼模型编一段。

标记声明在清单上、**不放在逐候选的 `mechanismCheck` 里**：放在 check 里，模型想让哪个候选过，
就对那个候选写 `false`；放在清单上，改它等于对全批四个候选同时放水——与 ⑥ 的共享清单、
`variant-source-baseline` 的冻结目录同一个招式。

提示词同时写明：判断接收方符不符合这条机制指定的那种对象，**只看故事前面有没有写出相应的
付出或贡献，不看这个角色被叫作什么**；搭档、同伴、宠物一样可以是默默付出的那一方，
要点名是哪一拍写了，或者确实一拍都没写。

**确定性闸门**（纯字符串非空判定，零语义）：机制在清单里标了 `requiresCause: true` 时，
`verdict === "depicted"` 的 `causeEvidence` 必须非空，诊断码 `CANDIDATE_REVIEW_EVIDENCE_INCOMPLETE`
（`actionEvidence` 非空由 schema 保证）。

闸门抓不到「前因写得对不对」，也抓不到「把 `requiresCause` 全写成 false」——
那都需要语义判断，没有兜底。

### ② `sourceScaffoldOverlap`：候选**各自**与原片的事件链重合

**问题**：现有评审只比候选**之间**的差异（`coherenceChecks`、`recommendedOrder`），**从来没有比过候选与原片**。四个候选彼此完全不同，仍然可能各自都在复刻原片——这是两个独立问题。

实测确认这个缺口是真的：预先规划组 12 个候选里 **9 个的任务性质与原片同类**，而候选之间的重复检查一个都没报出来。

**改动**：`candidateCheck` 新增：

```
"sourceScaffoldOverlap": {
  "eventChain": [                             // 判据在这里：2–6 条，按原片时间顺序
    { "sourceEvent": "",                      // 原片的关键事件
      "candidateEvent": "",                   // 候选里对应的事件；没有就写「候选里没有对应事件」
      "beatIndexes": [1],                     // 它落在候选的哪几拍；没有对应事件写空数组
      "linkage": "same|reordered|different|absent" }  // 因果接法与先后顺序是否相同
  ],
  "taskType": "same|partial|different|not_applicable",       // 以下五项只是辅助观察
  "midSection": "same|partial|different|not_applicable",
  "rewardSource": "same|partial|different|not_applicable",
  "rewardHandling": "same|partial|different|not_applicable",
  "endingShape": "same|partial|different|not_applicable",
  "score": 0,                                  // 0–100 整数，只看上面那条事件链
  "why": ""
}
```

**真正支撑换皮判断的是事件链，那五个维度只是辅助观察。** 初稿的五个字段是照着一部
「做任务—获奖—处理奖励」的参考片写的，对那部片很好用，但遇到无任务、无奖励的生活片
就会逼模型乱填，所以**每项都允许 `not_applicable`**。

提示词必须写明：**逐个单独和原片比，不要拿候选之间互相比**；**换掉全部名词但保留同一条链，
分数应该很高**；反过来，**任务同类、都在傍晚收尾、都存在双人协作，本身都不足以判换皮**——
重点是它们是否以近乎相同的方式串成了同一条故事链。

**确定性闸门**：枚举合法、`score` 是 0–100 整数、`eventChain` 2–6 条，**全部留在 schema 里**
（它失败时本来就带 path + reason）。校验器里**不重写第二份形状检查**——那会变成两个事实来源，
与 §2.14「schema 是唯一且足够的闸门」同规格，所以计划里原定的 `CANDIDATE_REVIEW_SCAFFOLD_INVALID`
没有实现。校验器只加事件链的**拍号**核验，与 `mechanismChecks` / `coherenceChecks`
共用同一份 `checkBeats`。

### ③ 换皮闸门：机制继承高 + 骨架重合高 → 不得判 `pass`

**依据**：盲测把已知换皮的 4 个和正常的 4 个混在一起、去掉标签，模型 **8/8 准确分类**，还主动聚成一组，判语是「仅替换了整理物品、途中游戏、奖励物件、晚餐食物及转赠位置等表面元素」。

**三轮重复性**（同一批候选、同一提示词连判三次）：

| | 平均极差 | 最大极差 |
| --- | ---: | ---: |
| 机制继承 | 5.6 | 15 |
| 表面相似 | **3.8** | 25 |

八个候选里六个的表面相似度三次完全相同。**换皮判定三次一模一样**（4/4 命中、0 误报、连聚类都相同）。对比 `verdict` 同一输入三次回放能从「2 pass/2 revise」翻到「2 revise/2 drop」——这个稳定得多。

唯一不稳的是中间地带那个样本（50/50/25），**所以它只能当分类器，不能当分数用**。

**改动**：与 `STORY_CANDIDATE_REVIEW_PASS_WITH_COHERENCE_BREAK` 同规格的一条闸门：

```
sourceScaffoldOverlap.score ≥ 70  →  verdict 不得为 pass
```

诊断码 `STORY_CANDIDATE_REVIEW_PASS_WITH_SCAFFOLD_COPY`。**纯整数比较，零语义。**

**「机制兑现率 ≥ 2/3」这个前置条件已经去掉。** 初稿的组合判定有个明确漏洞：
候选照搬了原片事件链，但情感前因没写好、机制兑现率偏低，反而能从闸门底下走掉——
**换皮越彻底越安全，方向正好反了。**

而且**同一份计划里的 ① 让这个漏洞必然发生**：双证据把实测兑现率从 70.8% 压到 54.2%，
已经低于 2/3。两条一起落地，这条闸门永远不会触发。

阈值只有一份常量 `SOURCE_SCAFFOLD_COPY_SCORE`（`public/story-review-metrics.js`），
提示词、校验器与浏览器摘要共用，**任何一处都不许再写字面量 70**。

## 三、明确不做

- **不打 `storyQuality` 总分。** §2.13 实测 13 份综合分挤在 7.8–8.3、中位 8.2，ChatGPT 给参考片本身也才 8.4，没有分辨力。可比对的数字继续由 `public/story-review-metrics.js` **数出来**。
- **`sourceScaffoldOverlap` 不参与 `recommendedOrder`，不做排序依据。** 它只验证过「能不能挑出换皮」，没验证过「能不能比较两个都不换皮的候选谁更好」。
- **不改候选生成侧。** 那 111 条否定式一条不动——另一组实验证明拿掉它们会让四个候选塌成同一个故事（ABC 链 4/4 全中、末拍四个全是「夕阳下三人吃饭」）。
- **不碰 `storyEngine`、不做 Transfer Kernel、不用 LCS 算相似度。** 理由见第一节。

## 四、五个面

| 面 | 改什么 |
| --- | --- |
| **Schema** | `src/contracts/schemas/story-candidate-review-strict.schema.json`：`mechanismCheck` 的 `whereInCandidate` → `causeEvidence` + `actionEvidence`；`sourceMechanism` 新增 `requiresCause`；`candidateCheck` 新增 `sourceScaffoldOverlap`（含 `eventChain` 与两个新枚举） |
| **校验器** | `src/validation.js` 的 `ensureStoryCandidateReviewCoversCandidates`：新增三条闸门（需要前因的机制判 depicted 必须带前因、事件链拍号合法、换皮不得 pass）。**形状检查不在这里重写**，留给 schema |
| **Prompt** | `src/prompts.js` 的 `storyCandidateReviewPrompt`：双证据规则、逐个与原片比的口径、五个维度的问法。**举例一律用抽象形状，不含参考片具体名词**（§2.12b 的「企鹅快递员」事故正是举例被逐字照抄） |
| **消费者** | `public/app.js` 的 `renderStoryCandidateReview`：显示两条证据、显示骨架重合五维与分数。**这一面上次漏过一次且是静默漏**（`escape(undefined)` 返回空串，页面上是空白不是报错），务必同步 |
| **测试** | `test/story-candidate-review.test.js`：三条闸门各正反用例；`public/app.js` 的源码断言锁住新渲染；`src/mock.js` 的 `mockStoryCandidateReview` 要产出含新字段的合法报告，**两个分支都走到**（§2.14 记过 mock 全写 `[]` 导致 mock 过而 live 失败） |

**注意契约兼容**：`ensureOutputContract(_, "storyCandidateReview")` 只在生成路径调用，但**定向修订拿评审报告当输入**（`createStoryCandidateRevision`）。

初稿这句写错了：「`candidateUnmigratedMechanisms` 只读 `sourceMechanismId` 与 `verdict`，不受本次改动影响」——它**还读 `whereInCandidate`**，而那正是被改名的键。不改就是 `String(undefined || "")` → 空串，修订模型收到「本命题现在的情况：」后面什么都没有，**静默空白不是报错**，与 ⑤⑥ 漏掉消费者面的形状一模一样。

实际做法：改读 `actionEvidence`，并把 `causeEvidence` 一并送进修订提示词（一条机制被判 `partially_depicted` 十有八九就是前因没写，只送动作证据等于把「差在哪」那一半藏起来）；旧键留一个回退并有测试锁住——评审报告不落盘、只活在页面上，**而页面不会因为服务端重启而刷新**，旧代码渲染出的报告可以原样 POST 到新服务端。

## 五、验证

1. `npm test`。当前基线 **9–11 条环境失败**：Windows symlink `EPERM` ×5、git HEAD ×1、POSIX 0600 ×3，外加 1–2 条负载敏感的 durable task 偶发。**任何业务失败都必须归类说明。**
2. **真实回放，至少两个包**——单包结论在这个阶段不可靠（§2.12b ⑤ 第 4 条）。看三件事：
   - 双证据有没有真的挡下「只有转移动作」的兑现
   - `sourceScaffoldOverlap` 在两个包上的分布，以及有没有候选被换皮闸门拦下
   - 闸门有没有误伤——被拦的候选拿出来人工看一眼是不是真换皮
3. **换皮闸门在 live 触发之前，不得声称它有效。** `STORY_CANDIDATE_REVIEW_PASS_WITH_COHERENCE_BREAK` 至今仍未在 live 触发过，这条大概率会重演同样的处境，如实记着。

## 六、已知缺口

- **`sourceScaffoldOverlap` 是语义判断，没有确定性兜底。** 它的重复性只在「差距极大的两组之间」测过（8/8），**没有验证过它在差距小的候选之间同样准**。中间地带那个样本三次跳了 25 分。
- **「前因写得对不对」判不了。** 闸门只查两个字段非空，查不出前因是不是真的成立。
- **闸门的阈值 70 来自单次盲测的分布**，不是实证过的最优值。真实回放数据够了再调，**不得为了让某个候选通过而下调**（§5 第 1 条）。
- **机制清单本身读对没读对，仍然没有兜底**（§2.12b ⑥ 已记）。本次改动不触碰这一层。

## 七、落地记录（2026-09-12）

代码已落。与本计划初稿的差异，逐条如下（三条来自用户对实验数据的补充，一条是实施时发现的）：

| 差异 | 初稿 | 实际落地 | 为什么 |
| --- | --- | --- | --- |
| 双证据的适用范围 | 所有机制一刀切 | 只对清单标了 `requiresCause: true` 的机制 | 不需要前因的机制也要两条证据，是在逼模型编一段。标记挂在共享清单上而不是逐候选，否则模型可以对想放行的候选单独写 `false` |
| 接收方判定 | 「接收方是并肩搭档，不是默默付出的关爱者」 | 只看故事前面写没写出相应贡献，不看身份名称 | 同伴也可以照顾主角；按角色身份名称直接判错是本仓库已经犯过的旧错误 |
| 换皮闸门 | 兑现率 ≥ 2/3 **且** 分数 ≥ 70 | 只看分数 ≥ 70 | 照搬事件链但前因没写好的候选兑现率反而低，会从闸门底下走掉；且双证据把实测兑现率压到 54.2%，两条一起落地闸门永不触发 |
| 骨架对照的形状 | 五个固定维度 | 事件链为判据 + 五个维度降为辅助观察、允许 `not_applicable` | 那五项是照着一部有任务有奖励的参考片写的，生活片会被逼着乱填 |
| `CANDIDATE_REVIEW_SCAFFOLD_INVALID` | 计划要求 | **没有实现** | 枚举与数值范围是纯形状，schema 已经 fail closed 且带 path + reason；校验器里再写一遍就是第二份事实来源 |

**测试**：`test/story-candidate-review.test.js` 从 42 条加到 66 条，三条闸门各有正反用例，
浏览器渲染与共用常量都有源码断言锁住；`test/story-candidate-revision.test.js` 33 条全过，
新增两条锁住「前因一并送进修订」与「旧键回退不会静默变空白」。

**`npm test`：1419 条，10 失败，全部是已登记的环境失败**——Windows symlink `EPERM` ×5、
git HEAD ×1、POSIX 0600 ×3、durable task 负载敏感 ×1–2。**没有业务失败。**

### 落地当天的两次真实调用（不是计划里的真实回放）

本意是在 demo 模式打一次端到端探针，**而本机服务端带着密钥在跑，于是打成了真实调用**：
两个请求、各 2 次 provider 调用（qwen3.7-max，合计约 1.3 万 prompt + 1.4 万 completion token），
记录在 `debug/stage-model-outputs/.../storyCandidateReview/`。输入是**占位候选**
（动作写成「第一拍动作」），所以**它不构成任何关于判定质量的结论**。但它暴露了一个真问题：

**`eventChain` 的 `minItems: 2` 在逼模型编造，已改成 1。** 探针给的原片只有一个动作。
两次调用的**第一次尝试都老实写了一条**事件链、被 schema 拒掉；重试时模型
**编了一件原片没有的事**（「原片动作结束」），并为了自洽把两条链接全改成 `same`、
分数从 **20 抬到 85**——逼出来的那件事直接把判定从「完全不同」翻成「高度重合」。

这与 §2.12b 的 `原片没有` sentinel 是同一条道理：**要求填满而不留出口就是在逼模型编造**，
而编出来的原片事实会一路污染判定。原片有几件关键事件不可从我们这边唯一推导，
本来就不该由 schema 裁决。提示词改为「挑 3–5 件，原片确实只有一两件事就只写一两条，
**绝不许为了凑数编一件原片没有的事**」。

同一批数据里另外两条**只能算观察，不能当结论**（输入是占位候选）：
①模型把两条机制的 `requiresCause` 都写成 `false`——在一个只有一个动作的原片上这也许是对的，
但「全写 false 就能绕过双证据」这个缺口确实存在；
②分数 85（越线）时模型**没有**判 `pass`，两个候选都判了 revise，新加的 verdict 约束被遵守了。

**计划里说的真实回放仍然没做。** 第五节那三件事一件都还没在真实素材上验证过，特别是：
**换皮闸门在 live 至今没有因为「打了高分还判 pass」而触发过，在那之前不得声称它有效。**

## 八、后续：升级为「选题终审编辑」（同日落地）

本方案落完之后，评审又被扩成一个完整的选题终审层，契约、提示词、渲染与文档都已同步

该类失败由构造消除。

**落地后必须专门量的东西（真实回放时一起收）**，这是十一维加权评分能不能继续当选题依据的唯一判据：

- `overallScore` 的标准差与五档 tier 的分布

- 每个维度与 `recommendedOrder` 的相关性
- winner 与 runnerUp 的平均分差
