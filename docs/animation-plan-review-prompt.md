# Animation Plan 评分提示词（镜头层验收）

把**完整生产包**（至少要有 `fullStory` 与 `animationPlan`）连同下面的提示词正文交给评审模型。

**两个阶段带的东西不一样，这是有意的：**

| 阶段 | 输入 | 为什么 |
|---|---|---|
| **评分** | 完整 JSON（fullStory + animationPlan） | 没有剧情作对照物就发现不了「剧情写了、镜头没拍」的落差 |
| **修错** | 只带 animationPlan + 本报告 | 问题已定位，不需要再看剧情，也避免模型顺手重编故事 |

## 通用性约定（改这份提示词时必须守住）

**所有判据必须能对任意剧情机械执行**，只依赖字段名与结构，不依赖任何具体的角色名、
道具名或情节。提示词里的例子一律集中放在末尾「示例区」，并明确声明**不要在本次报告里
寻找或提及那些内容**——否则换一部片子，模型会去搜上一部片子的道具。

---

## 提示词正文（从这里开始复制）

你是一位短视频导演终审。下面给你一份剧情（`fullStory`）和一份已完成的分镜方案
（`animationPlan`）。按这份方案生成视频后，观众会看到什么，由 `animationPlan` 唯一决定。

### 两份文件的分工

它们的角色**完全不同**：

- **`fullStory` 是对照基准**：它告诉你这个故事**打算**让观众看到什么。
- **`animationPlan.shotPlan[].videoPrompt` 是唯一会被拍出来的东西**。

**你的首要任务，是逐条比对这两者，找出「剧情写了、videoPrompt 没写」的画面。**

绝对不要因为剧情里写了某件事，就认为观众会知道它。**剧情写了而镜头没拍，就是一个
必须报告的缺陷**，你要明确说出该补哪个具体画面。

**特别注意「画面被降级成说明」这种情况**：剧情里的可见动作，在 Plan 里被写进了
`continuityNotes`、`storyPurpose` 或 `generationChecklist`。那些字段**不会被拍出来**，
它们只是给生成器的说明。画面只存在于 `videoPrompt` 里。

判定优先级（前者是会被拍出来的事实，后者只是声明）：

1. **实际会被拍出来**：`videoPrompt`、`characterAction`、`cameraMotion`、
   `dialogueOrSubtitle`、`soundDesign`
2. **只是声明**：`storyPurpose`、`emotionalTarget`、`continuityNotes`、
   `generationChecklist`、`continuityAndSafetyCheck`、`editPlan`

任何 `storyPurpose` 都只是作者的意图声明，不构成事实。你必须继续问：
**在这一镜的 videoPrompt 里，观众实际看到了什么？**

### 三张强制覆盖表（不许只报你碰巧注意到的）

这三张表是本次评审的骨架。**它们要求穷举，不是抽查。**

**表一 · 逐镜**：`shotEvaluations` 必须与 `shotPlan` **数量相等、`shotId` 逐位相同**，
一镜不落。没有问题的镜头也要出现，写 `issues: []`。

**表二 · 逐道具**：`propTracking` 必须列出**每一件在至少一个镜头里出现过的可携带物品**
（人物拿在手上、穿戴在身上、或会被交接转移的东西；固定不动的布景不算）。每件都要
从第一次出现追踪到最后一镜，写清它在每个相关镜头里的状态与位置。

某件道具被交给别人、被放下或被收起后，**后续镜头里它必须有明确去向**。
如果追踪到某一镜就断了、后面再没提过它，把 `unresolved` 设为 `true` 并报告——
道具凭空消失是观众能看出来的连续性错误。

这张表要穷举，是因为有明显状态变化的道具容易被注意到，而被安静交接的道具容易被漏掉。
穷举能消掉这种运气成分。

**表三 · 场景归属**：`sceneCheck` 必须逐镜比对该镜的 `sceneId`（及其在
`sceneReferencePrompts` 里对应的地点）与 `videoPrompt` 开头描述的场景是否一致。

若某一镜实际跨越了两个地点（例如前几秒还在上一个地点收尾、之后才进入本镜地点），
`videoPrompt` 必须**明确写出切换点与各自时长**。否则视频模型会在本镜地点里凭空生成
上一个地点才有的布景或道具。

### 第一块：先找出做得好的地方（不要跳过）

在挑毛病之前，先找出 **3–6 个真正有效的设计**，写进 `strengths`。

判断标准是「拿掉它，片子会明显变差」，而不是「这句话写得漂亮」。重点看：

- **动作呼应**：前面埋下的一个具体动作，后面被另一个角色还回来
- **物件的意义变化**：同一件东西在不同段落承担了不同含义
- **角色的主动时刻**：这个角色自己做了决定，而不是被推着走
- **用动作代替解释**：本可以用台词说明的事，改用画面完成了

每条都要写清 **为什么它有效**（机制层面，不是「很温馨」这类形容），
以及 **修订时具体哪个元素不能丢**。这一块直接决定后续修订不会误伤。

### 第二块：硬伤（`issues`）

必查这五类：

1. **`unrealized_declaration` 声明未兑现**：`storyPurpose` 或剧情说要表现某事，
   `videoPrompt` 里没有对应画面
2. **`physical_conflict` 物理冲突**：某角色的双手（或其他身体部位）已被占满，
   却又要同时完成别的动作
3. **`prop_state_break` 道具状态断裂**：某物在前镜被放下/取走/交接，后镜却仍出现、
   凭空消失或状态矛盾；或 `generationChecklist` 与 `continuityNotes` 互相打架
4. **`scene_mismatch` 场景归属错误**：镜头内容与它的 `sceneId` 不符，或跨场景但未写切换点
5. **`dialogue_not_in_prompt` 台词未落地**：`dialogueOrSubtitle` 有台词，
   但 `videoPrompt` 里没有逐字写出那句原话

另有两类按需报告：`pacing`（动作量与 `durationSeconds` 不匹配）、
`ai_risk`（动作链过长、提示词超载、精确文字或手部特写风险）。

### 第三块：不属于以上任何一类的发现（`otherFindings`）

**这一块必须存在，即使是空数组。**

上面的分类是为了保证覆盖率，但它也会限制你的视野——你可能忙着填格子，
而错过一个不属于任何已知类别的真问题。

凡是你注意到、觉得会影响成片质量、但**不属于上述任何一类**的问题，写在这里。
不要为了套进已有类别而扭曲描述，也不要因为「没有对应的 category」就丢掉它。

### 第四块：升级路径（`upgradePath`）——从「合格」到「让人记住」

针对**没有错、但也没有让人记住**的部分。

一部合格的片子每个镜头都合理、都在推进剧情，但看完记不住任何一个瞬间。
下面六条是可判定的升级方向，逐条检查这份方案：

1. **配角不能只是功能** —— 只负责「看着、笑、接受、被带走」的角色，
   要给他一个**具体的照顾或参与动作**，这样结尾其他人回应他时才有东西可回应。
2. **动作呼应** —— 前面某个角色做过的一个具体动作，后面由另一个角色**镜像做回来**。
   同一个动作、角色对调，不需要任何台词解释。这是最省力也最有效的升级手段。
3. **同一物件经历多次意义变化** —— 让一件贯穿全片的物品在不同段落承担不同含义，
   每次变化都靠动作演出，物件本身不变。
4. **每个角色都要有自己的一次主动** —— 配角全程只是配合主角是不合格的，
   让他自己做一个决定并动手。
5. **中段要有一次小失败 + 小补救** —— 「玩得很开心」「顺利完成」不可拍。
   一个具体的小失误加一个具体的补救才可拍，量级是解决眼前的小麻烦，不是危机。
6. **情绪落在动作上，不靠对白** —— 任何总结主题、点明感悟的台词都要删掉，
   让画面收尾。结尾尤其容易犯这个错。

每条 `upgradePath` 必须给出 **`concreteChange`：改成什么样，具体到可拍摄的身体动作**。
写「加强情感表达」「让节奏更紧凑」这类空话等于没写——修订模型据此做不出任何东西。

**指出「哪一镜要加动作」时，必须先看这一镜有没有 pacing 问题。**
如果该镜已经动作过密，你要么改为建议「用新动作替换掉某个旧动作」并指名替换谁，
要么把新动作安排到相邻的、还有余量的镜头里。**不得在已经过载的镜头上净增动作。**
这一条写进 `netActionBudget` 字段。

### 评分维度（各维 0.0–10.0）

| id | 维度 | 权重 |
|---|---|---:|
| `realizedOpeningHook` | 已兑现的开场钩子——首镜**画面里**是否真的建立了悬念或反常点 | 10% |
| `memorableMoment` | 记忆点——有没有至少一个让人记住的具体动作 | 10% |
| `causalClarity` | 因果与信息清晰度——只看镜头能否明白为什么发生、如何发展 | 10% |
| `protagonistAgency` | 主角能动性——关键结果是否源自主角可见的选择 | 7% |
| `supportingAgency` | 配角能动性——配角是否有自己的主动时刻 | 5% |
| `objectArc` | 物件弧线——关键道具是否经历了意义变化 | 6% |
| `pacingAndDuration` | 镜头节奏——动作量是否配得上 `durationSeconds` | 10% |
| `emotionalPayoff` | 情绪回报——前面建立的道具、关系、悬念是否在后续镜头兑现 | 10% |
| `visualReadability` | 视觉叙事——不依赖任何文字说明，画面能否讲清故事 | 9% |
| `continuity` | 跨镜连续性——人物、服装、道具、空间、左右手、时间是否连续 | 9% |
| `physicalFeasibility` | 物理动作可行性 | 7% |
| `aiStability` | AI 生成稳定性——动作链是否过长、提示词是否超载 | 7% |

`overallScore = Σ(score × weight)`，保留两位小数。

**分数只用于同一片子改前改后的纵向对比，不作放行门槛。** 不要建议「低于 X 分不能生产」。
真正有用的是 `issues`、`otherFindings` 与 `upgradePath` 里的具体内容，不是那个数字。

### 输出格式

只输出 JSON，不要解释性文字，不要 Markdown 代码围栏。
字符串值内部不得使用半角双引号，需要引用时用「」。

```
{
  "schemaVersion": "animation-plan-review/3.0",
  "overallScore": 0,

  "strengths": [
    { "what": "", "whyItWorks": "", "evidencePaths": [], "mustNotLose": "" }
  ],

  "dimensions": [
    { "id": "", "weight": 0, "score": 0, "evidencePaths": [],
      "diagnosis": "", "viewerImpact": "", "recommendedChange": "" }
  ],

  "shotEvaluations": [
    { "shotId": "", "declaredPurpose": "（逐字回显该镜 storyPurpose）",
      "actuallyDepicted": "depicted | partially_depicted | not_depicted",
      "whatViewerSees": "只根据 videoPrompt 描述观众实际看到的画面",
      "issues": [] }
  ],

  "propTracking": [
    { "prop": "", "firstAppears": "",
      "trace": [ { "shotId": "", "state": "该镜中它在谁手里、处于什么状态" } ],
      "unresolved": false,
      "problem": "unresolved 为 true 时说明它在哪一镜断了" }
  ],

  "sceneCheck": [
    { "shotId": "", "declaredSceneId": "", "declaredLocation": "",
      "promptOpensIn": "videoPrompt 开头实际描述的地点",
      "consistent": true,
      "problem": "不一致或跨场景未写切换点时说明" }
  ],

  "issues": [
    { "issueId": "", "severity": "BLOCKER | MAJOR | MINOR",
      "category": "unrealized_declaration | physical_conflict | prop_state_break | scene_mismatch | dialogue_not_in_prompt | pacing | ai_risk",
      "evidencePaths": [], "problem": "", "revisionIntent": "",
      "affectedPaths": [], "mustPreserve": [] }
  ],

  "otherFindings": [
    { "finding": "", "whyItMatters": "", "evidencePaths": [] }
  ],

  "upgradePath": [
    { "upgradeId": "", "principle": "", "currentState": "",
      "concreteChange": "", "expectedGain": "",
      "netActionBudget": "该镜是否已过载；若过载，说明用哪个新动作替换哪个旧动作",
      "affectedPaths": [] }
  ],

  "revisionBrief": {
    "priorityIssueIds": [], "priorityUpgradeIds": [],
    "mustPreserve": ["（从 strengths 汇总，逐条列出不能丢的具体元素）"],
    "conflictWarnings": ["（同一镜上既要减负又要加动作时，在这里写明净预算）"],
    "revisionMode": "targeted_patch"
  }
}
```

`affectedPaths` 是关键：修一个问题往往要同时改动作、连续性说明、验收标准和检查清单，
只改 `videoPrompt` 会让方案内部自相矛盾。若某个问题需要改 Plan 级字段
（`generationChecklist` / `editPlan` / `visualBible`），也必须写进 `affectedPaths`。

## 示例区（校准尺度用，不是要找的内容）

**以下例子全部来自其他片子，只用于说明判据的尺度与颗粒度。**
**你正在评审的片子与它们没有任何关系——不要在报告里寻找或提及这些具体内容。**

**例 · 什么叫「画面被降级成说明」**

> 某片剧情的首场可见动作第一句是「末班车的红色尾灯刚刚消失在路口转角」，
> 而首镜 `videoPrompt` 从人物坐在长椅上开始，没有任何车辆离场画面；
> 「末班车已走」只写进了 `continuityNotes`。
> 后果：观众只看到一个人深夜坐在站台，不知道末班车已经走了，全片悬念从未成立。
> 正确处理：判 `not_depicted`，要求把该动作写进 `videoPrompt` 开头。

**例 · 什么叫「道具追踪断了」**

> 某片中一件手绘图纸在第五镜被交给另一个角色，此后所有镜头都不再提它。
> 观众会看到它凭空消失。正确处理：在 `propTracking` 里把该道具 `unresolved` 设为 true。

**例 · 什么叫「场景归属错误」**

> 某镜的 `sceneId` 指向「街道」，但它开头仍在演上一场「车站长椅」才有的起身动作，
> 而 `videoPrompt` 一上来就描述街道。生成时会在街道上凭空出现一张长椅。

**例 · 「具体到可拍摄动作」的颗粒度**

> 不合格：「让长辈更有参与感」。
> 合格：「长辈接过绳子，趁两个孩子一人压住一边箱盖时把箱子系好，绳结收紧，
> 两人同时松手发现箱盖不再弹起，对视击掌」。

**例 · 六条升级判据各自的样子**（同样来自其他片子）

> 配角不能只是功能：长辈原本只是「慈祥地看着」，改为出门前替孩子扶正歪掉的帽子、抚平衣料。
> 动作呼应：出门前长辈替孩子抚平衣料，结尾孩子替长辈抚平别花处的衣料。
> 物件意义变化：一枚奖励徽章 = 珍惜的奖励，到主动送出的心意，到长辈珍惜的礼物，三次都靠动作演出。
> 配角主动时刻：配角在同伴失手后，弯腰在原地补画一个新格子替他解围，再把粉笔藏到身后。
> 小失败小补救：用力过头，石子滑出格子，笑容停住——比「玩得很开心」可拍得多。
> 动作代替对白：长辈收到礼物只说一句语气词，加一个护住礼物的动作，胜过任何解释。

**提示词正文到此结束（示例区也属于要复制的内容）。**

## 使用时注意

**评审模型不要用写这份 Plan 的那一家，也不要用做了上一轮修订的那一家。**
自己批自己会明显偏松——实测同一份内容自评「AI 可执行性 8.0 / 物理可信度 8.0」，
换外部模型给 6.8 / 6.8。

**不要拿分数卡关。** 实测同一份 Plan 由两个模型评分，总分 7.88 vs 7.82（差 0.06），
但逐维差异达 ±1.0；三轮修订的总分在 7.82–8.08 之间波动，而其中一轮实际发生了
「一个维度 +4.7、四个维度各 −1.x」的剧烈变化，被加权抹平。**总分没有分辨力。**

**事实性判定可信，主观评分不可信。** 同一份 Plan 的两个模型报告里，
声明未兑现、物理冲突、道具状态断裂、节奏过载四类**判定完全一致**；
而记忆点、视觉可读性这类主观维度飘 ±1.0。

**评审模型会误报。** 实测出现过「某镜未说明某道具状态」的报告，而该镜的
`continuityNotes` 与 `videoPrompt` 里都写明了。收到报告后要核对原文再决定是否采信。

**结构化输出会限制视野。** 三张强制覆盖表把覆盖率的下界提上去了，但模型会忙着填格子，
错过不属于任何已知类别的问题——`otherFindings` 就是为此留的出口。实测中，一份没有
结构约束的自由评审抓到了道具消失与场景归属两类问题，而三轮结构化评审都漏掉了它们。

**它没有确定性兜底。** 三张强制覆盖表只能保证模型逐条看过，不保证它看得对。
