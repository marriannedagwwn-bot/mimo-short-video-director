# Animation Plan 评审与定向修订 · 落地方案

大白话版。要解决的问题、怎么做、以及三个需要你拍板的地方。

---

## 一、这套东西是干什么的

Animation Plan 生成完之后，加一个「评分」按钮。点了之后：

1. 让一个 AI 通读剧情和分镜，挑出问题，同时说清楚哪些地方做得好
2. 你看报告，决定要不要修
3. 点「按报告修订」，让 AI 只改被点名的那几个镜头
4. 服务端自动检查改得对不对，不对就打回去让它重改一次

**为什么需要它**：现在所有校验器都只管「格式对不对、字段全不全」，
没有任何东西检查「剧情里说的事，镜头里到底拍没拍出来」。

实测的典型例子：剧情第一句写「末班车的红色尾灯刚刚消失在路口转角」，
而首镜的提示词从「女孩坐在长椅上看地图」开始，一帧车都没有。
「末班车已走」只写进了 continuityNotes——那是给生成器的备注，不会被拍出来。
结果观众根本不知道末班车走了，全片赖以成立的悬念从头到尾没建立过。

## 二、整条链路长什么样

```
Animation Plan 生成完
   ↓
[评分] 按钮 ──→ 评审模型（吃剧情 + 分镜）
   ↓
服务端校验报告格式  ← 不合格就打回，最多重试一次
   ↓
报告展示给你看（做得好的 / 硬伤 / 升级建议）
   ↓
[按报告修订] 按钮 ──→ 修订模型（只吃分镜 + 报告）
   ↓
服务端校验修订结果  ← 不合格就带着诊断打回，最多重试一次
   ↓
合并进 Plan
```

**评分时给完整 JSON，修订时只给分镜。** 这不是随便定的：
没有剧情作对照物，就发现不了「剧情写了、镜头没拍」；
而修订阶段问题已经定位好了，再给剧情只会让模型顺手重编故事。

## 三、已经做好的部分

**评审提示词**（`docs/animation-plan-review-prompt.md`）

判据全部只认字段结构，不认具体剧情——换任何一部片子都能用。
所有举例都隔离在末尾「示例区」，并明确写了「不要在报告里找这些内容」。

要求 AI 交三张必须写满的表：
- 每个镜头逐个评（不许只挑几个说）
- 每件道具从头追到尾（防止道具凭空消失）
- 每个镜头核对场景归属（防止在错误的地点生成上一场的布景）

外加一个 `otherFindings` 出口：不属于任何已知分类的问题写这里。
加它是因为实测发现，结构化输出会让模型忙着填格子而错过没见过的问题类型。

**确定性校验器**（`src/animation-plan-review-validation.js`）

只数数，不做主观判断。两个函数：

- `ensureReviewReportContract` — 逐镜逐场景有没有写满、引用的镜头号是不是真实存在、
  道具的两个状态标记有没有互相矛盾、12 个维度齐不齐
- `ensureRevisionContract` — 修订有没有偷偷改时长和场次归属、六个可写字段全不全、
  **被判过拥挤的镜头有没有净增动作**

最后一条是核心，下面单说。

## 四、最难的一关：怎么防止修订把镜头改得更挤

**问题**：修订时 AI 总想往镜头里加东西。而被判「太挤」的镜头，再加就更挤。

**试过三次，全都没用**：

1. 提示词里写「注意不要太满」→ 它加了
2. 改成「不允许净增加」→ 它加了，还在摘要里写「本镜只替换未净增」
3. 再补一句「不要自称只替换而实际增加」→ 它换个说法：
   「这四个是细节，均并入原有动作链，不增加独立动作段」

**根本原因**：「一个动作」没有客观定义。判定权在 AI 手里，它就永远有解释空间。

**解法：把判定权拿走。** 要求修订输出必须列两个清单：

```
removedActions: ["小白子轻轻摸芙芙猫的猫头"]
addedActions:   ["纸条第一次只塞到一半卡住"]
```

服务端只做一件事：**数数组长度**。被判过拥挤的镜头，删的必须不少于加的。

效果立竿见影——同一份输入，两个模型都老老实实报了数：
一个写「删 2 加 7」，另一个写「删 2 加 4」，全被拦下。
而在这之前，同样的行为它描述成「不增加独立动作段」，根本无从查证。

**然后带着诊断让它重改一次，两个模型都一次就过：**

```
第一次：删 2 加 7  ✗ 被拦
诊断：「你新增 7 个动作但只删除 2 个，受约束镜头必须删≥加」
重试：删 1 加 1  ✓ 通过
```

重试后的结果反而更好——第一次它加了 7 个动作把镜头塞满，
重试后只留下终审真正要求的那一个，其余为了丰富细节而加的全放弃了。

**这里有个反直觉但重要的结论**：

| | 有没有用 |
|---|---|
| 事前在提示词里定规矩 | 没用，三次加码都没用 |
| 事后拿数字打回去重做 | 有用，两个模型都一次过 |

事前规矩是抽象的，AI 能解释；事后诊断是算术，没法辩。
所以**修订必须设计成「允许第一次做错」**，而不是指望一次做对。

## 五、传输不稳定，必须有兜底

昨天 30 次真实调用，**大约三分之一失败**。分四种：

| 情况 | 表现 | 怎么办 |
|---|---|---|
| 连不上 | 3 秒就报错 | 立刻重试，几乎没成本 |
| 中途断线 | 跑了几百秒才断，token 已经烧了 | 重试；同一个模型连断三次就换一家 |
| 撞我们自己的超时 | 900 秒被掐，其实它还在正常出字 | 评审阶段单独配 1800 秒 |
| AI 说胡话 | 一直输出重复的垃圾直到撑爆上限 | 检测到输出不是合法 JSON 就换模型重来 |

**换模型兜底是实测有效的**：有一份输入 qwen3.8 连试三次全断，kimi 一次就过。

另外发现**同时跑两个请求时失败率明显更高**，而评审本来就是手动点一次的低频操作，
排队串行做就行。

（更彻底的解法是把「总超时」换成「多久没出字就算断」，
已单独写在 `docs/stream-idle-watchdog-plan.md`，不在本次范围。）

## 六、已定下的三件事（2026-09-06）

### 1. 评审报告不落盘 ✅

跟现在的剧情体检同规格：只返回给页面显示，刷新就没了，不进 Artifact、不进 lineage、
不参与派生、不 stale 任何东西。第一版完全不碰 Artifact 系统。

### 2. 修订结果先预览，确认后才签发 ✅

修订完成后**不自动写回 Plan**。先把改动展示出来（原文与修订版并排），
你看过觉得可以，再手动确认签发新的 Plan revision。

这样做的好处是把「作废该变体全部已生成媒体」这个重代价推迟到你确认那一刻，
而不是修订一跑完就发生。实测中修订第一次输出常常是要被打回的，
自动签发会造成大量无谓的 revision 和媒体作废。

### 3. 评审允许换模型兜底，但必须写明 ✅

实测依据：有一份输入 qwen3.8 连续三次断线（656s / 11s / 413s），kimi-k3 一次就过。
同模型反复重试是浪费，换一家就好了。

评审不产生 Artifact、不进 lineage，换模型只影响这一次报告的内容，
所以放宽「不得静默切换 provider/model」这条限制是安全的。

**但不得静默**：报告里必须如实记录本次实际使用的 provider 与 model，
以及是否发生过换模型兜底。页面上也要显示，因为不同模型的评分口径有差异
（实测同一份 Plan 两个模型总分差 0.06，但逐个维度能差 ±1.0）。

## 附：原始的三个待定问题
### （已由上面的决定取代）

### 1. 评审报告存不存？

**不存**（推荐）：跟现在的剧情体检一样，只在页面上显示，刷新就没了。
好处是完全不碰 lineage，改动最小。

**存**：作为新的 Artifact 类型进 lineage。好处是能对比「改前改后」，
坏处是要处理 revision、digest、依赖关系、什么时候作废，工作量大得多。

### 2. 修订结果算不算新的 Plan 版本？

修订会改动分镜内容，按现有规矩这应该签发新的 Plan revision，
并且**作废该变体已经生成的所有媒体**（图片、视频都得重做）。

要确认的是：这个代价你接受吗？还是希望修订结果先只是「预览」，
你看过觉得行了再手动确认签发？

### 3. 评审可以换模型吗？

现在的规矩是「不得静默切换 provider/model」。
但评审换模型的兜底实测有效，而且评审不产生 Artifact、不进 lineage。

建议：**允许换，但必须在报告里写明实际用了哪个模型**，不静默。

## 七、实施顺序

前提是上面三个问题有了答案。按风险从小到大：

1. **加评审阶段**——新 API 端点、走现有的 stage 路由、单独配 1800 秒超时。
   报告只返回给页面，不落盘。
2. **加修订阶段**——新端点，输入是分镜 + 报告，输出走 `ensureRevisionContract`。
   被拦就带诊断重试一次，再被拦就保持原 Plan 不动、如实报错。
3. **接页面**——Plan 卡片下面加「评分」按钮，报告用可折叠面板展示，
   每条问题旁边给「按这条修订」。
4. **补测试**——校验器的单元测试、重试流程的集成测试。
   传输那部分用假的 SSE 响应测，不打真实接口。

第 1 步做完就能用起来（手动看报告、手动改），
第 2 步才需要处理「修订结果怎么进 Plan」这个较重的问题。
