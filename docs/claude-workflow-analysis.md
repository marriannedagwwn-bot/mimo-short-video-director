## 7. Claude 的常见工作流程

去除明确 fork 后的 17 条谱系中，本地解析器近似识别出 3,058 次搜索/读取命令、479 次测试命令、347 次 Git 检查和 251 次静态/构建检查。这个计数只是行为频率，不是质量评分；它说明 Claude 的默认模式确实偏向“先读、再改、再测”，但能否闭环取决于是否继续走到真实运行和用户可见结果。

常见有效流程是：

```text
用户要求
  → 找出权威数据与不可变契约
  → 阅读生产者、消费者、校验器、Prompt、测试
  → 用历史语料或真实失败复现
  → 提出可被否证的根因
  → 最小修改或确定性派生
  → 定向测试
  → 完整回归
  → 真实服务/真实产物/浏览器验证
  → 对照用户预期
  → 检查 Git diff、提交与当前保留状态
```

失败通常发生在中间提前结束：停在“完整回归通过”，没有继续到真实 provider、产品启动方式、真实成片或用户审美验收。

## 8. Claude 修改代码时的有效方法

### 8.1 先确定权威来源和不变量

direct-shot 3.1 把 `fullStory.sceneScript[].timeRange` 定为镜头数量和时长的权威，服务端派生骨架，模型无权改写。对白补写最终也采用同样思路：`dialogueOrSubtitle` 是权威，模型只给 insertion，原文拼接由服务端完成。此类设计比“让模型再输出一份完整对象”稳定。

### 8.2 调查完整调用链，而不是只改报错位置

失败 token 样本从模型记账作用域追到错误对象、服务端响应信封、前端 API 包装、阶段 catch 和最终文案。direct-shot 同时检查 workflow、prompt、provider 能力、前端汇总和测试。历史中这种跨生产者/消费者调查能显著减少半成品修复。

### 8.3 用真实语料约束修改范围

多个成功样本在动代码前先统计本地真实数据：305 个场次的时长分布、64 次 postpass、180 份 Full Story、历史对白匹配分布、真实七镜包。这让阈值、边界和失败频率有来源，也能发现“计划前提不成立”。

### 8.4 最小化模型可写范围

有效 repair 都遵循“服务端持有 path、digest、authority；模型只返回最小 replacement/addition/insertion；合并后从头复验”。`c96c538` 对 `c474efe` 的修正直接证明：要求模型复述长原文会失败，最小插入更可靠。

### 8.5 隔离用户已有改动

多窗口开发时，Claude会检查 hunk 归属、只暂存自己的文件，或用临时 worktree 验证提交。虽然偶尔因 stash 语义误判出错，但随后改用更可靠的隔离方式。当前仓库正处于类似脏工作树环境，这条尤其重要。

## 9. Claude 调试代码时的有效方法

### 9.1 先区分确定性缺陷与概率问题

一份可复现反例足以证明代码路径存在确定性 bug，但不能估计模型发生频率。FS-01 组在用户质疑后明确作出这一区分，是本次最重要的方法论之一。

### 9.2 让每个假设有可否证结果

真实 pipeline 样本先认为“缺场景参考图”是根因；加入上一镜连续性帧后同时修复地点、圆圈和道具状态，于是撤回原假设。故事截断样本也逐个否证“提示词更长”“最后一条约束”“供应商整体变更”等假设。有效调试不是坚持第一解释，而是缩小剩余解释空间。

### 9.3 回放失败输入，而不是只写新 fixture

多个高价值修复都把真实失败 JSON 原样喂回当前代码，并做修复前/修复后对照。角色边界误伤、对白 repair merge、旧包摄影连续性都因此能证明“同一输入，旧代码失败，新代码通过”。

### 9.4 检查实际运行中的程序版本

`ab29ca2a` 中，修复落盘后用户仍撞同一错误，最后发现服务是更早启动的 `node server.js`，没有 watch。进程启动时间、文件修改时间和 debug 时间的交叉对照，成功区分“代码没修好”和“运行的是旧代码”。

### 9.5 检查入口差异

MiniMax worker 在 import 测试中先完成模块初始化，因此全部通过；产品以子进程直接执行，在文件前部顶层 await 时访问后部 `const`，必然 TDZ。加入真正的子进程测试才封住该缺口。工程验证必须覆盖产品实际入口。

## 10. Claude 验证结果时的有效方法

### 10.1 静态验证（A）

常见做法包括 `node --check` 全仓扫描、Schema 验证、契约测试和全套 `npm test`。它们能证明语法、类型形状、确定性不变量和已覆盖回归，但不能证明用户体验。

### 10.2 自动化行为验证（B）

高质量样本会先跑最小测试文件，再跑全套；失败后根据具体 assertion 更新实现或确认 fixture 已过时。direct-shot 3.1、离场规则、dialogue repair 都保留了失败到通过的完整轨迹，而不是只展示最后绿灯。

### 10.3 真实运行验证（C）

有效做法包括启动真实服务、检查端口和 HTTP、调用真实或受控 provider 路径、核对 debug 落盘、读取最终 Artifact、用 ffmpeg 对成片检测切点。`47754ac4` 是最完整的 C 类闭环。

### 10.4 用户可见结果验证（D）

成功 token 样本检查了错误状态文案；供应商错误码样本在真实浏览器中比较改前/改后文本；故事质量样本则让用户观看视频并指出“仍差点意思”。D 类证据经常推翻 A/B 类乐观结论。

### 10.5 当前代码复验

本次复盘在当前脏工作树上只做只读测试：

- Node：`v24.19.0`
- 8 个相关测试文件：89/89 通过
- `npm test` 三次：前两次 925/926，均失败于当前未提交的 `durable-task-manager` watchdog 测试；该用例单独运行通过；第三次全套 926/926 通过

这组结果本身就是一个现场例子：一次全绿或一次失败都不足以判断非确定性/时序测试；还要隔离运行、复跑并记录波动。该测试属于分析开始前已存在的用户工作，本报告不诊断、不修改它，也不把它归因于 Claude 历史样本。

## 11. Claude 的典型失败模式

### 11.1 把局部或低层验证外推为端到端稳定

FS-01 组将 H3 单镜首轮合规和固定剧情端到端数据外推到项目稳定性，但用户实际还会卡在 Seedance、Context-IR 和视频阶段。正确做法是先定义端到端边界，再确认样本覆盖所有用户实际路径。

### 11.2 代理指标与用户真实问题错位

故事“同配置”指标把地点与角色组合绑定；模型只让配角离场，指标从 4/6 降到 3/6 并不报警，但地点仍 5/6 相同，视觉依然单调。Prompt 要求“生活细节”也被宠物微动作字面满足。代理变量能计算，不代表它测到了用户关心的事。

### 11.3 验证入口与产品入口不一致

worker import 测试无法发现子进程执行顺序；源代码改了但未重启服务，用户仍在跑旧逻辑；固定 provider/固定剧情压测没有覆盖用户切换后的路径。这类问题往往会造成“测试都过、产品必坏”。

### 11.4 在无恢复路径上加高命中硬门

对白原话检查回扫旧语料命中率很高，但 direct-shot 对已解析失败当时没有 retry。硬失败让昂贵生成变成反复重跑，直到用户真实反馈后才补有界 repair。新增硬门之前必须先检查错误是否可恢复、成本和命中率。

### 11.5 对模型提出不可靠的逐字复述要求

第一版 dialogue repair 让模型返回完整改写后的长 `videoPrompt`，守卫又要求原文逐字不变，结果模型合理改写措辞后必然被拒。模型只应返回最小插入内容，原文冻结与拼接由确定性代码完成。

### 11.6 样本不足却给出频率结论

FS-01 中用户直接指出计划要求约 40 镜头，而当时只验证一条输出。Claude随后纠正：一条反例证明缺陷存在，但不能证明发生率和修复收益。这个纠正应前置成规则，而不是等用户指出。

### 11.7 工具操作本身造成假象

历史中出现过 stash 不含未跟踪文件导致旧提交验证假红、错误解析脚本参数、`lsof` 无输出被反向解释、错误使用 stash/复制导致修复暂时被覆盖。每个关键操作后都应重新读取状态，而不是相信命令意图等于实际状态。

## 12. “测试通过但用户目标未达到”的案例

### 案例 A：生活细节与萌点

- 代码：`0893c74` 后全套 855/855。
- 自动化证明：prompt 中确实存在“至少两场生活细节”和“大幅度身体动作”等文本约束。
- 真实输出：只新增宠物舔爪和打呼，主角动作幅度不变；地点仍 5/6 相同；时长从 44 秒增到 65 秒。
- 用户目标：故事要更生活化、有氛围和明显萌点。
- 结论：A/B 通过，D 未通过。Prompt 字面合规不是效果合规。

### 案例 B：故事候选结构

- 代码：strict Schema、关键拍投影和结构分化测试持续全绿。
- 自动化证明：字段完整、投影精确、候选结构签名不同。
- 真实结果：用户看生成视频后仍认为剧情不够好；Claude发现冲突过早消失、五场同人物配置、配角台词承担解释功能。
- 当前代码证据：README 仍明确写着 5×4 回放可全部通过 Schema/精确投影，而人工仍会发现状态和动作顺序矛盾。
- 结论：结构正确是必要条件，不是故事质量充分条件。

### 案例 C：对白补写

- 代码：第一版 repair 后 890/890。
- 真实结果 1：Qwen 因 prompt 没出现 `JSON` 字样返回 HTTP 400。
- 修正后仍 890/890。
- 真实结果 2：模型返回完整重写提示词，merge 因原文变化拒绝；随后改为 insertion。
- 结论：本地 mock 没覆盖供应商特殊协议，也没验证模型会否遵守不现实的长文本逐字复述要求。

### 案例 D：MiniMax worker

- 代码：import 级测试和多次 A/B 出片通过。
- 产品结果：spawn 子进程直接执行时访问顶层 await 后声明的常量，抛 TDZ。
- 修复：`6024af5` 把常量前移，并新增子进程级测试。
- 结论：测试必须走与产品一致的入口。

## 13. 可以迁移给 Codex 的规则草案

以下 15 条有直接历史证据支持；最后 2 条是基础工程底线，不能伪装成 Claude 独有经验。待用户确认后，再以独立章节追加到现有 `AGENTS.md`，不覆盖原内容。

### 13.1 历史证据支持的规则

1. 开始修改前，必须把用户可观察的验收标准写成可检查项，并分别标出 A 静态、B 自动化、C 真实运行、D 用户可见验证；不得用 A 替代 D。
2. 修改前必须阅读当前实现、调用方、下游消费者、校验器、Prompt 和现有测试；数据契约改动必须逐项列出这些影响面。
3. 能复现的问题必须先用真实失败输入或最小反例复现；修复后必须让同一输入通过，并保留回归测试。
4. 每次修改必须对应一个可被证伪的假设；新证据否定假设时必须明确撤回并重新诊断，不能继续在旧假设上堆补丁。
5. 必须区分确定性缺陷与概率问题：一个稳定反例可证明缺陷存在，但成功率、稳定性和泛化结论必须有足量、多路径样本。
6. 优先做能解释问题的最小修改；能由权威上游唯一派生的值必须由服务端确定性派生，不让模型重新猜测或复述。
7. 不得顺手重构与任务无关的代码；脏工作树或多窗口环境中只暂存自己确认过的 hunk，并在操作后复查状态。
8. 修改后先运行针对性测试，再运行必要的完整回归；测试失败必须根据具体失败内容重新诊断，不得重复盲改或只重跑等待偶然通过。
9. 必须读取测试的实际断言、错误路径和输出内容，不能只看退出码或“tests passed”总数；characterization 测试通过不得解释为缺陷已修。
10. 现有测试缺少本次行为或产品入口覆盖时，必须补能证明该行为的回归测试或可重复验证脚本；import 测试不能代替产品实际使用的 CLI、spawn、服务或浏览器入口。
11. UI、工作流、生成结果、provider 或 worker 任务必须验证产品实际入口：运行中的服务版本、真实响应信封/日志、最终 Artifact 或成片、用户可见文案至少检查一项。
12. 新增校验门前必须检查命中率、失败成本和恢复路径；高频且可安全局部化的错误要配一次有界修复，无法安全修复的才 fail closed。
13. 局部修复必须只让模型返回最小 replacement/addition/insertion；原文冻结、path、digest、authority、合并和完整复验由服务端控制。
14. 用户指出结果不符合预期时，必须优先重查验收标准、实际运行路径和真实输出，不得把现有测试继续全绿当作反驳。
15. 最终汇报必须列出修改文件、执行命令、实际结果、当前分支是否保留、未覆盖路径和剩余风险；没有 C/D 证据时不得声称“完全解决”。

### 13.2 基础工程规则

16. 不允许通过放宽正确断言、删除校验、跳过测试或只挑通过的输出制造成功；契约确实变化时必须说明旧断言为何失效，并增加新契约的正反例。
17. 结束前必须检查 `git diff --check`、完整 diff 和工作树状态，确认没有意外文件、敏感信息或无关修改；未经要求不得提交或推送。
